The one thing you need

Patience with things that look stuck. The single most expensive mistake in this whole process is pressing Ctrl+C on a command that is actually working. AWS is a server-side state machine: your terminal is a window onto it, not a switch. If something looks frozen, run a describe in a second terminal — never cancel.

Two commands that look identical and are not

kubectl get pods failing with Unauthorized and failing with Forbidden are different problems with different fixes. You will meet both. See the troubleshooting section.

01  The two-tool split

The concept that explains most of the confusion in this runbook

This stack is built with two tools that do not know the other exists. Terraform builds the network. eksctl builds the Kubernetes cluster. Each keeps its own record of what it owns, in a different place.

QuestionTerraformeksctl
Where is its memory?terraform.tfstate (local file)CloudFormation stacks (in AWS)
What if the memory is lost?Terraform no longer knows it owns anythingNothing — AWS holds it
Delete commandterraform destroyeksctl delete cluster
Does it clean up the other's resources?NoNo
Why not do everything in one tool?

You can — Terraform has an EKS module. But each tool is genuinely better at its half: Terraform models dependencies between explicit resources, while eksctl knows the ~20-object ritual EKS requires and does it in one command. Learning both, and knowing where the seam is, is more useful than picking one and fighting it.

02  Cost & discipline

Read this before you run anything, and again before you walk away

EKS is not free, and two of its charges are easy to miss because they do not scale with what you are actually using.

What you didMonthly if left runningWhat stopping it requires
Nothing — fresh account₹0—
VPC only (terraform apply)~₹3,800terraform destroy
+ EKS cluster~₹10,200eksctl delete cluster
+ 2 nodes~₹13,000same command — it takes the nodegroup too
+ ALB Ingress~₹14,800kubectl delete ingress before the cluster
The order that costs money if you get it wrong

The ALB is owned by the Kubernetes controller, not by AWS automation. If you uninstall the controller while an Ingress object still exists, nothing in the cluster knows about the load balancer any more. It stays in your account, invisible, billing ~₹1,400/month until somebody finds it in the console.

Delete the Ingress first. Always. The teardown section has the exact sequence.

The habit

  • Build it, learn on it, tear it down the same day. Two hours of EKS costs about ₹40.
  • Never leave it up "just in case." A rebuild is one terraform apply and one eksctl create cluster.
  • Verify the teardown, don't assume it. Every teardown step in this runbook ends with a command whose output proves it worked.
  • Keep the ECR repository and the IAM policy. Both cost nothing and make the next rebuild faster.
A safe exception

Stopping (not terminating) an EC2 instance with a 30 GB volume costs nothing if your account is in its first 12 months — EBS storage is inside the free tier. That is why the runbook uses a stoppable "admin box" rather than terminating it.

Phase 1  Terraform: the VPC

Terraform/ · 14 resources · ~4 minutes

Fourteen resources describe a network shaped for Kubernetes: a VPC, two public and two private subnets across two Availability Zones, an Internet Gateway for the public ones, and a NAT Gateway so the private ones can still reach the internet outbound.

Terraform/main.tf — provider pinning 
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

The version constraint matters more than it looks. AWS provider ~> 5.0 will not silently jump to v6, where some resource arguments changed. Pin, then upgrade deliberately.

Run it

cd Terraform
terraform init
terraform plan          # read this — expect exactly "14 to add"
terraform apply
terraform output        # copy the IDs — the next four phases need them

Save the outputs somewhere you can reach them. They are the addresses of everything you just built:

terraform output 
vpc_id                = "vpc-0475e4a8c8fdc4a52"
public_subnet_ids     = ["subnet-009dd86fb8453154f", "subnet-01e805407bc958957"]
private_subnet_ids    = ["subnet-0f7d7f7dafd38bc5e", "subnet-082db3dc8f0cd7be1"]
internet_gateway_id   = "igw-08e5ae149d16c6d9a"
nat_gateway_id        = "nat-0f37b4d01f3796f35"
These IDs change on every rebuild

Destroy then re-apply and you get entirely new subnets. Never hardcode them into notes that outlive one session, and never assume an ID from a previous session still exists. Always re-read terraform output.

Checkpoint

Apply complete! Resources: 14 added, 0 changed, 0 destroyed. — and the NAT gateway takes about 1m45s, which is normal and is the slowest part.

Two things your VPC needs for Kubernetes

Both are one-liners in vpc.tf and both are hard requirements:

resource "aws_vpc" "my-vpc" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true    # EKS will not work without this
  enable_dns_hostnames = true    # nodes need private DNS names
}

Without DNS hostnames, nodes register with the cluster but kubelet cannot resolve ip-10-0-x-x.region.compute.internal, and the nodes never join.

Phase 2  Tag the subnets

Pure AWS CLI · ~30 seconds · the step everyone forgets on rebuild

You never tell the load balancer controller which subnets to use. It discovers them by reading AWS resource tags. No tags means it finds nothing, creates nothing, and reports nothing — the classic silent failure.

On your machine — paste your own IDs from terraform output 
export CLUSTER_NAME=ai-interview-platform-eks
export PUB1=subnet-009dd86fb8453154f      # public, ap-south-1b
export PUB2=subnet-01e805407bc958957      # public, ap-south-1a
export PVT1=subnet-0f7d7f7dafd38bc5e      # private, ap-south-1a
export PVT2=subnet-082db3dc8f0cd7be1      # private, ap-south-1b
export VPC=vpc-0475e4a8c8fdc4a52

# Public subnets → internet-facing load balancers
aws ec2 create-tags --resources $PUB1 $PUB2 \
  --tags Key=kubernetes.io/role/elb,Value=1

# Private subnets → internal load balancers
aws ec2 create-tags --resources $PVT1 $PVT2 \
  --tags Key=kubernetes.io/role/internal-elb,Value=1

# All four → usable by this cluster
aws ec2 create-tags --resources $PUB1 $PUB2 $PVT1 $PVT2 \
  --tags Key=kubernetes.io/cluster/$CLUSTER_NAME,Value=shared
create-tags prints nothing on success

Silence is the success signal. A typo in the subnet ID fails loudly, but a typo in the tag key silently writes a tag nothing will ever read. Always verify with the describe below.

Checkpoint — every row must show a value in elb or internal, and cluster=shared 
aws ec2 describe-subnets --filters "Name=vpc-id,Values=$VPC" \
  --query 'sort_by(Subnets,&CidrBlock)[].{Cidr:CidrBlock,AZ:AvailabilityZone,
    elb:Tags[?Key==`kubernetes.io/role/elb`]|[0].Value,
    internal:Tags[?Key==`kubernetes.io/role/internal-elb`]|[0].Value,
    cluster:Tags[?Key==`kubernetes.io/cluster/ai-interview-platform-eks`]|[0].Value}' \
  --output table
If you manage tags in Terraform, this is where you will lose an hour

A lifecycle { ignore_changes = [tags] } block on your subnets means Terraform silently discards any tag you put in vpc.tf. The tags never appear, and plan reports no changes. To manage these in code you must delete the ignore_changes block first — there is no error message to tell you this.

Why this phase is worth doing even though it feels manual

These tags are the only thing that connects your VPC to the load balancer controller. Getting them right is what makes phase 12 work, and getting them wrong is the number one cause of a load balancer that never appears.

Phase 3  EKS cluster

eksctl · ~15–20 minutes · the long one

One command creates roughly twenty AWS objects: the control plane, a managed node group, two IAM roles, an OIDC provider, security groups, and the ENIs that connect the control plane to your subnets. Then it writes your kubeconfig.

On your machine — run from the repo root 
eksctl create cluster \
  --name $CLUSTER_NAME \
  --region ap-south-1 \
  --version 1.36 \
  --vpc-private-subnets=$PVT1,$PVT2 \
  --vpc-public-subnets=$PUB1,$PUB2 \
  --nodegroup-name default \
  --node-type t3.small \
  --nodes 2 --nodes-min 2 --nodes-max 3 \
  --node-private-networking \
  --managed \
  --with-oidc
FlagWhat it does, and why it is set that way
--vpc-*-subnetsTells eksctl to use your existing VPC instead of building its own. It will not create route tables or NAT gateways — those must already exist.
--node-private-networkingPuts the worker nodes in the private subnets. They reach the internet outbound via the NAT gateway, and have no public IP.
--managedA managed node group — EKS owns the Auto Scaling group and handles rolling updates. The default on recent eksctl, but explicit is clearer.
--with-oidcRegister the cluster's OIDC issuer in IAM. Required for IRSA in phases 11–12. Skipping it is the number one reason a controller "starts but does nothing."
--version 1.36Omit to let eksctl pick its tested default. Check aws eks describe-cluster-versions first if you pin one.
Do not interrupt this, no matter how stuck it looks

eksctl prints waiting for CloudFormation stack every 30 seconds with no spinner and no progress bar. It looks frozen. It is not — it is polling AWS.

Ctrl+C kills only your local watcher. AWS keeps building. You then have a half-finished cluster, no kubeconfig written, and a bill running. If you must check progress, open a second terminal:

Second terminal — safe to run, safe to Ctrl+C 
while true; do
  echo "--- $(date +%H:%M:%S) ---"
  aws eks describe-nodegroup --cluster-name $CLUSTER_NAME --region ap-south-1 \
    --nodegroup-name default \
    --query 'nodegroup.[status,health.issues]' --output json 2>/dev/null \
    || echo "nodegroup not created yet"
  sleep 60
done
Checkpoint — 2 nodes Ready, no EXTERNAL-IP (they are private) 
kubectl get nodes -o wide
kubectl get pods -n kube-system
aws eks list-addons --cluster-name $CLUSTER_NAME

Expect two nodes in Ready, and eight pods all Running with zero restarts:

PodCountKindWhat it does
aws-node-*2 (2/2)DaemonSetVPC CNI — gives each pod a real address from your subnet CIDR
kube-proxy-*2DaemonSetPrograms the network rules that make Services work
coredns-*2DeploymentCluster DNS — service-name resolution
metrics-server-*2DeploymentFeeds kubectl top and horizontal autoscaling
Where the node IPs come from

Each node gets a private address from the subnet CIDR it was launched in — something like 10.0.11.x and 10.0.12.x. If you see addresses from 172.31.x.x instead, the nodes landed in the default VPC, not yours: --node-private-networking did not take effect.

If it fails, this is the command that tells you why

aws eks describe-nodegroup … --query 'nodegroup.health.issues'. EKS names the cause directly. The two most common codes are NodeCreationFailure — usually a missing node-role permission or no outbound internet — and InsufficientFreeAddresses.

Phase 4  ECR repository

~10 seconds · do this once, keep it forever

ECR is where the pipeline pushes your built image. Create it before the first pipeline run, or the push fails with name unknown: The repository does not exist. 

aws ecr create-repository \
  --repository-name ai-interview-dev-platform/frontend \
  --region ap-south-1 \
  --image-scanning-configuration scanOnPush=true
The slash is part of the name

ai-interview-dev-platform/frontend is a single repository name that happens to contain a slash — not a folder path. The pipeline builds its image reference as $REGISTRY/$ECR_REPO/frontend:$SHA, so the repository must be named exactly that. Creating ai-interview-dev-platform alone will not work.

Checkpoint 
aws ecr describe-repositories --region ap-south-1 \
  --query "repositories[].[repositoryName,repositoryUri]" --output table
Deliberately skipped: IMMUTABLE tags

Immutable tags are the best practice, but they mean re-running a failed workflow on the same commit fails with tag already exists. While you are learning and re-running often, leave the default (MUTABLE). Turn it on once the pipeline is stable.

Optional: stop images accumulating

aws ecr put-lifecycle-policy \
  --repository-name ai-interview-dev-platform/frontend \
  --region ap-south-1 \
  --lifecycle-policy-text '{"rules":[{"rulePriority":1,"description":"Keep last 10",
    "selection":{"tagStatus":"any","countType":"imageCountMoreThan","countNumber":10},
    "action":{"type":"expire"}}]}'

Phase 5  Keyless IAM role

The part that means no AWS credential exists anywhere

GitHub Actions needs permission to push to ECR and talk to your cluster. The usual approach is to create an AWS user, generate an access key, and paste it into GitHub as a secret. This runbook does something better: no key is created at all.

5a — Register GitHub as an identity provider

aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com

This says "tokens signed by GitHub are worth reading." It grants nothing on its own — permission comes entirely from the trust policy in 5c.

5b — Write the trust policy

Replace <ACCOUNT_ID> and the repo name, then save as trust.json:

trust.json 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      // the provider you registered in 5a
      "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        // who the token is FOR — must be AWS
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",

        // who the token is FROM — pin the exact repo and branch
        "token.actions.githubusercontent.com:sub": "repo:OWNER/REPO:ref:refs/heads/main"
      }
    }
  }]
}
Two ways to get the sub claim wrong

1 — Branch vs environment. A job with no environment gets repo:OWNER/REPO:ref:refs/heads/main. A job that declares environment: production gets repo:OWNER/REPO:environment:production instead. Copy the wrong form and every deploy fails with Not authorized to perform sts:AssumeRoleWithWebIdentity and no explanation.

2 — Wildcards. "repo:OWNER/*" accepts tokens from a fork, a pull request, or an unrelated repository. If you need several branches, use StringLike with an explicit pattern — never a bare wildcard.

5c — Create the role and its permissions

permissions.json — exactly what the pipeline needs 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      // can only be granted account-wide; by itself it lets you log in,
      // not read or write any repository
      "Effect": "Allow",
      "Action": "ecr:GetAuthorizationToken",
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability", "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart", "ecr:CompleteLayerUpload",
        "ecr:PutImage", "ecr:BatchGetImage"
      ],
      "Resource": "arn:aws:ecr:ap-south-1:<ACCOUNT_ID>:repository/ai-interview-dev-platform/frontend"
    },
    {
      // only enough to build a kubeconfig for this one cluster
      "Effect": "Allow",
      "Action": "eks:DescribeCluster",
      "Resource": "arn:aws:eks:ap-south-1:<ACCOUNT_ID>:cluster/ai-interview-platform-eks"
    }
  ]
}
aws iam create-role \
  --role-name gh-deploy-frontend \
  --assume-role-policy-document file://trust.json

aws iam put-role-policy \
  --role-name gh-deploy-frontend \
  --policy-name deploy-permissions \
  --policy-document file://permissions.json
What is deliberately missing

No ecr:DeleteRepository, no iam:*, no ec2:*, no eks:UpdateClusterConfig, and no access to any other repository or cluster. If this role were ever assumed by someone hostile, the worst they could do is push one image and read one cluster's description.

Checkpoint

aws iam get-role --role-name gh-deploy-frontend --query Role.Arn returns the ARN. Note it — this is the value for the AWS_DEPLOY_ROLE_ARN secret in phase 7.

Phase 6  Cluster access

The single most misunderstood step in EKS

Your IAM role can now authenticate to AWS. That does not mean Kubernetes will let it do anything. AWS IAM and Kubernetes RBAC are two separate authorization systems, and a cluster has to be told about an IAM principal before it recognises it.

On your machine — grant the deploy role access to one namespace only 
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

# 1. tell the cluster this IAM role maps to a Kubernetes identity
aws eks create-access-entry \
  --cluster-name $CLUSTER_NAME --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:role/gh-deploy-frontend \
  --type STANDARD

# 2. give that identity admin rights in ONE namespace only
aws eks associate-access-policy \
  --cluster-name $CLUSTER_NAME --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:role/gh-deploy-frontend \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
  --access-scope type=namespace,namespaces=default

type=namespace,namespaces=default is the important part. The pipeline is an admin of the default namespace and a nobody everywhere else — it cannot read secrets in kube-system, and it cannot touch cluster-scoped objects at all.

Also add your own user, for kubectl

If your CLI user is not the cluster creator, it needs an entry too:

aws eks create-access-entry \
  --cluster-name $CLUSTER_NAME --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:user/<YOUR_IAM_USER>

aws eks associate-access-policy \
  --cluster-name $CLUSTER_NAME --region ap-south-1 \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:user/<YOUR_IAM_USER> \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSAdminPolicy \
  --access-scope type=namespace,namespaces=default
Checkpoint — the role must appear in this list 
aws eks list-access-entries --cluster-name $CLUSTER_NAME
aws eks list-associated-access-policies --cluster-name $CLUSTER_NAME \
  --principal-arn arn:aws:iam::${ACCOUNT_ID}:role/gh-deploy-frontend

Access policies, from least to most

PolicyGrantsUse it for
AmazonEKSViewPolicyread only (get/list/watch)a pipeline that only inspects
AmazonEKSEditPolicyread + write workloadsa CI pipeline that deploys
AmazonEKSAdminPolicyedit + RBAC & quotas in a namespacea deploy role that must also manage Roles
AmazonEKSClusterAdminPolicyeverything, cluster-widehumans. Never a CI role.
You can stack them, each with its own scope

Associating a second policy does not replace the first. Each keeps its own access scope, so a common shape is read-only across the whole cluster plus write access in one namespace. Re-running associate-access-policy for a policy you already have updates its scope rather than duplicating it.

Phase 7  GitHub configuration

~5 minutes · two secrets, one variable

Everything the workflow needs, in one table. Note how little of it is sensitive.

WhereNameValueSensitive?

Secrets vs variables

A secret is encrypted and masked in logs. A variable is visible. An ARN is an identifier, not a credential — putting it in a variable means you can read it back when debugging, and the logs stay readable. Reserve secrets for actual secrets.

Match the workflow to your account

Four values at the top of the workflow file, plus two in the Sonar properties:

.github/workflows/pipeline.yml 
env:
  AWS_REGION: ap-south-1
  EKS_CLUSTER: ai-interview-platform-eks
  K8S_NAMESPACE: default
  ECR_REPO: ai-interview-dev-platform
sonar-project.properties 
sonar.projectKey=<YOUR_ORG>_<YOUR_REPO>
sonar.organization=<YOUR_ORG>
sonar.sources=src
sonar.tests=src/test
sonar.javascript.lcov.reportPaths=coverage/lcov.info
Permissions per job replace the workflow default

The workflow starts at contents: read. If you add a permissions: block to a job, it replaces the default entirely — so you must list every permission that job needs, including contents: read. Forgetting that is why a job suddenly cannot check out the repo.

Phase 8  SonarCloud

~10 minutes · two settings that will otherwise cost you an hour

SonarCloud tracks bugs, code smells, duplication and coverage over time, and comments on pull requests. It is genuinely useful, and it has two setup traps that produce confusing errors.

8a — Create the organisation and import the project

  1. Sign in at sonarcloud.io with GitHub.
  2. Create or join an organisation. Its key is usually your GitHub username or org name.
  3. Import your repository as a project.
  4. Note the organisation key and the project key. For a GitHub import the project key is normally <org-key>_<repo-name>.

The most reliable way to get the exact values is the product itself:

Your project → Administration → Analysis Method → With GitHub Actions. That page generates a snippet already populated with your own keys. Copy from there rather than guessing.

8b — Generate a token and store it

My Account → Security → Generate Token. Copy it once (it is shown only once) and add it to GitHub as the SONAR_TOKEN repository secret.

Trap 1 — the properties file wins

If you copied a tutorial's sonar-project.properties and it still points at the tutorial author's organisation, the scanner will dutifully look for their project. The error is: 

ERROR Not authorized or project not found. Please check the 'SONAR_TOKEN'
environment variable, the 'sonar.projectKey' and 'sonar.organization' properties,
or contact the project administrator to verify the token's permissions.
A project with the same key may already exist in another organization.

That last sentence is the clue. Binding your project in the SonarCloud UI is not enough — the properties file overrides it. Fix the two keys.

Trap 2 — Automatic Analysis blocks CI analysis

When you import a GitHub repo, SonarCloud may switch Automatic Analysis on — a mode where SonarCloud analyses your code itself, server-side, with no CI involved. Running both at once is refused: 

ERROR You are running CI analysis while Automatic Analysis is enabled.
Please consider disabling one or the other.

Turn Automatic Analysis off, keep CI analysis. Go to Administration → Analysis Method and disable it.

Why CI analysis is the one you want

Automatic Analysis cannot produce code coverage. Your Vite config generates an lcov report and the properties file points at it — all of which Automatic Analysis silently ignores. It also has no branch analysis, and no accessible logs, which is exactly what you need when something goes wrong.

8c — Make it a real gate

By default SonarCloud reports and the workflow continues. To make a failed quality gate actually fail the build, add the wait parameter to the scanner: 

# in sonar-project.properties
sonar.qualitygate.wait=true
sonar.qualitygate.timeout=300
This blocks the job

The scanner will poll SonarCloud until the quality gate resolves, up to the timeout. That is the point — but it does add a minute or two to every run. Worth it once you trust your coverage numbers; noisy before that.

Checkpoint

Push a trivial change and watch the app job. A green SonarQube Scan step with Load quality profiles (done) and Load active rules (done) in the log means it authenticated and analysed successfully.

Phase 9  First deploy

Run it manually first — never discover a missing secret during a push

The workflow is triggered by a push, a pull request, or manually. For the first attempt, use the manual trigger: it exercises the identical path, but on your schedule, and you can read the logs without a commit in the way.

Actions → CI/CD Pipeline → Run workflow.

Trivy prints a beautiful table and the step goes green unless you set exit-code: '1'. Same for SonarCloud's quality gate. The exit code is the entire difference between a report and a gate — check for it whenever you add a scanner.

Checkpoint

All four jobs green, and the Actions summary shows the commit, image tag, cluster and namespace. If the deploy job never started, look at its if: condition — a refs/heads/master check on a main repository skips silently.

Phase 10  Verify it runs

Free · nothing in AWS is created

The pipeline deployed a Deployment and a Service. The Service is ClusterIP — a virtual address that exists only inside the cluster's network. Nothing outside can reach it yet.

Point kubectl at the cluster, then look 
aws eks update-kubeconfig --region ap-south-1 --name $CLUSTER_NAME

kubectl get pods -n default -o wide
kubectl get deploy,svc -n default
Run that as two separate commands

Pasting both on one line without a newline between them merges them — the cluster name becomes …-ekskubectl and you get a confusing "not found". The kubeconfig is then never written, and kubectl falls back to its built-in default of http://localhost:8080.

dial tcp 127.0.0.1:8080: connection refused means no kubeconfig, not "the cluster is down".

Reach it with a port-forward

This tunnels through the API server you are already authenticated to. No load balancer, no security group change, no public IP, no cost. 

kubectl port-forward -n default svc/frontend 8080:80
# leave it running, then open http://localhost:8080

What you should see

The app's login page. The seed-account shortcuts at the bottom are controlled by APP_ENV from the ConfigMap — if they are visible, the whole ConfigMap → env var → entrypoint → browser chain works.

Prove that chain explicitly 
curl -s http://localhost:8080/runtime-config.js
// Generated at container start by docker-entrypoint.sh. Do not edit.
// window.__APP_CONFIG__ = { apiBaseUrl: "", appEnv: "dev" };
Login will fail — and that is expected

The frontend is configured same-origin (apiBaseUrl: "") and there is no /api route yet, so nginx's SPA fallback answers API calls with index.html and HTTP 200. The app receives HTML where it expected JSON and reports "the server returned a web page instead of data".

That is the frontend working correctly against a backend that has not been deployed. It is a phase boundary, not a bug.

Phase 11  ALB Ingress controller

Steps 11a–11c are per-cluster · ~10 minutes · nothing billable yet

To get a public URL, something has to create a load balancer on your behalf. The AWS Load Balancer Controller is a pod inside your cluster that watches for Ingress objects and builds an ALB in response.

Not to be confused with

There is an older controller called aws-alb-ingress-controller. It is deprecated. The one you want is aws-load-balancer-controller, a Kubernetes SIG project. Tutorials mix them up constantly.

11a — The controller needs an AWS identity (IRSA)

The controller pod calls EC2, ELB and ACM APIs. It gets permission through IRSA — IAM Roles for Service Accounts, which needs the OIDC provider you created back in phase 3 with --with-oidc.

Checkpoint first — the issuer must already be registered in IAM 
aws eks describe-cluster --name $CLUSTER_NAME --region ap-south-1 \
  --query "cluster.identity.oidc.issuer" --output text

aws iam list-open-id-connect-providers

# one ARN must end with the same id as the issuer URL:
# issuer …/id/8CF248A9F796CD8E2FAE8DEB0B673B37
# arn   …:oidc-provider/oidc.eks.ap-south-1.amazonaws.com/id/8CF248A9F796CD8E2FAE8DEB0B673B37

If it is missing, register it now:

eksctl utils associate-iam-oidc-provider \
  --cluster $CLUSTER_NAME --region ap-south-1 --approve

11b — Create the controller's IAM policy

AWS publishes the exact policy the controller needs. Download it — do not hand-write it — and pin it to the same version as the chart you are about to install.

Find the current version, then download the matching policy 
helm repo add eks https://aws.github.io/eks-charts

Phase 12  Public URL

One YAML file · the only phase you repeat for each app

Everything so far was plumbing. This is the object that actually asks for a load balancer.

k8s/alb-ingress.yml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend
  annotations:
    # internet-facing = a public ALB. Use "internal" for a private one,
    # which is what the internal-elb subnet tag from phase 2 is for.
    alb.ingress.kubernetes.io/scheme: internet-facing

    # ip, not instance: pods hold real VPC addresses, so the ALB reaches
    # a pod directly instead of hopping through a NodePort on the host.
    alb.ingress.kubernetes.io/target-type: ip

    # the path the ALB polls to decide a pod is healthy — a cheap
    # endpoint, deliberately not the homepage
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
kubectl apply -f k8s/alb-ingress.yml -n default
Every Service named in the rules must already exist

The controller resolves all of them when it builds its plan. One missing Service fails the whole thing — you get no load balancer at all, not a partial one.

This matters for the next phase of this project: the app has no /api backend yet, so keep the Ingress to a single / rule. Adding an /api → middleware path before that Service exists will silently produce nothing.

Wait — twice

kubectl get ingress -n default -w
WaitDurationWhat is happening
First2–3 minADDRESS goes from empty to an …elb.amazonaws.com hostname. AWS is provisioning the ALB.
Second1–2 minDNS propagates and the target passes its first health check. Until this finishes, curl fails even though the address exists.
Confirm — after both waits 
export ADDR=$(kubectl get ingress frontend -n default \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')

echo "http://$ADDR"

# -sS, not -s: the capital S shows WHY it failed. -s alone hides the error.
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' "http://$ADDR/"
Reading the exit codes

200 = working. 000 = could not connect at all (usually still provisioning, or DNS not yet resolved). 503 = the ALB exists but no target is healthy — check your healthcheck-path.

What a 200 here actually proves

It confirms the entire chain at once: the subnet tags were right, the controller discovered the subnets by tag alone, built an ALB across two different AZs, registered the pod's private IP as a target, the health check passed, and the security group allows port 80 from the internet. Every one of those has to be true for a 200.

Where to verify it in the console

EC2 → Load Balancing → Load Balancers (confirm you are in the right region — ALBs are regional). Open your load balancer and look at the Network mapping tab: two Availability Zones, each with one of your public subnets. Then EC2 → Target Groups → your target group → Targets: the pod's private IP, marked healthy.

Cost from this moment

~$0.0225/hr ≈ ₹1,400/month, plus per-request LCU charges. Fine for an afternoon. Expensive to forget. And the ALB lives exactly as long as the Ingress does — which is why the teardown section starts by deleting the Ingress.

Four steps, fixed order, ~15 minutes

  1. 01

    Delete the Ingress

When it breaks

Every failure in this runbook, with its actual cause

Authentication & permissions

Not authorized to perform sts:AssumeRoleWithWebIdentity

The trust policy does not match the token GitHub sent. In order of likelihood:

  1. The sub uses the branch form but the job declares environment: — GitHub sends …:environment:production instead.
  2. The owner or repo name is misspelled. It is case-sensitive.
  3. The OIDC provider was never created in this account.
  4. aud is not exactly sts.amazonaws.com.

Add a temporary step printing ${{ github.repository }} and compare character by character. There is no message that tells you which of the four it is.

Credentials could not be loaded / no OIDC token available

The job is missing permissions: id-token: write. Remember that a job-level permissions: block replaces the workflow default, so you must re-list contents: read too.

kubectl: Unauthorized

No access entry for this principal. EKS recognises the AWS identity but has no Kubernetes mapping for it. Fix with create-access-entry + associate-access-policy — see phase 6.

Remember this can happen even to a role with AdministratorAccess. AWS permissions and Kubernetes permissions are separate systems.

kubectl: Forbidden (cannot get pods in namespace …)

The entry exists but the policy is too narrow, or the scope does not cover what you asked for. A policy scoped to namespaces=demo returns Forbidden when you query default.

Fix by re-running associate-access-policy with a wider --access-scope; re-running updates the scope rather than duplicating.

The distinction to memorise: Unauthorized = authentication, no entry. Forbidden = authorization, entry but wrong policy.

kubectl: dial tcp 127.0.0.1:8080 connection refused

There is no kubeconfig. localhost:8080 is kubectl's built-in fallback when it finds no configuration at all. Run aws eks update-kubeconfig — and check you ran it as one command, not two merged onto a single line by a lost newline.

Kind of works

The nodegroup sits in CREATING for 25+ minutes and then eksctl times out

eksctl's 25-minute wait is client-side only. When it gives up, AWS keeps building. This is not a failure — it is your terminal giving up on watching.

The documented cause is nodes not joining within 15 minutes, which EKS reports as NodeCreationFailure. Check the real state with: 

aws eks describe-nodegroup --cluster-name $CLUSTER_NAME --region ap-south-1 \
  --nodegroup-name default --query 'nodegroup.[status,health.issues]' --output json

The two common causes are a missing node-role permission (usually AmazonEKS_CNI_Policy) and no outbound internet from the private subnets — the latter happens if the NAT gateway or its route is missing.

I pressed Ctrl+C during eksctl — is it broken?

Probably not. Ctrl+C kills the local process; the CloudFormation stack keeps building. Wait, then check: 

aws cloudformation wait stack-create-complete \
  --stack-name eksctl-$CLUSTER_NAME-cluster
echo "exit=$?"      # silent while waiting — that is correct

If the cluster stack completed, do not re-run eksctl create cluster — it will fail with "stack already exists". Instead run only the phase it never reached: eksctl create nodegroup …, then aws eks update-kubeconfig (eksctl writes the kubeconfig only at the very end).

The pod is stuck in ImagePullBackOff

Two causes. Either the image reference still literally says IMAGE_PLACEHOLDER (the sed did not match — which is why the pipeline has a grep guard), or the node role lacks permission to pull from ECR. 

kubectl describe pod -n default -l app=frontend | tail -30
kubectl get pods returns "No resources found" after a successful deploy

Usually the namespace. The pipeline deploys to K8S_NAMESPACE from the workflow's env: block. Check you are looking in the same one.

Load balancer

The Ingress ADDRESS stays empty forever, with no error anywhere

Subnet tags. This is the silent failure the whole design of phase 2 exists to prevent. The controller discovers subnets by tag alone; no tag, no candidates, no error.

You need two subnets tagged kubernetes.io/role/elb=1 in two different AZs. One is not enough — an ALB refuses to be created in a single AZ.

Re-run the phase 2 verification query.

Controller logs say couldn't auto-discover subnets

Phase 2 again — but check the cluster tag specifically. A kubernetes.io/cluster/<name> tag naming a different cluster actively excludes that subnet from discovery. If the name does not match --name exactly, remove the tag rather than guessing.

Controller logs say AccessDenied or NoCredentialProviders

IRSA. The ServiceAccount annotation is missing, or the trust policy names the wrong namespace or ServiceAccount. Re-run the phase 11c checkpoint — if it prints a blank line, that is your answer. 

kubectl get sa aws-load-balancer-controller -n kube-system \
  -o jsonpath='{.metadata.annotations.eks\.amazonaws\.com/role-arn}{"\n"}'
failed calling webhook … context deadline exceeded

The control plane cannot reach the controller's webhook on port 9443. This is the least guessable failure in the whole process. Allow it on the cluster security group: 

export CLUSTER_SG=$(aws eks describe-cluster --name $CLUSTER_NAME --region ap-south-1 \
  --query "cluster.resourcesVpcConfig.clusterSecurityGroupId" --output text)

aws ec2 authorize-security-group-ingress --region ap-south-1 \
  --group-id $CLUSTER_SG --protocol tcp --port 9443 --source-group $CLUSTER_SG
The ALB exists but returns 503

No healthy targets. Either the health check path returns something other than 200, or the pods are not ready. Check EC2 → Target Groups → Targets in the console — it names the reason per target.

Ingress created, no ALB, and no errors anywhere

Two causes. Either a Service named in the rules does not exist (the controller resolves all of them at once — one missing Service produces nothing), or ingressClassName: alb is missing or misspelled.

curl returns 000 even though ADDRESS is populated

You did not wait twice. The address appears before the ALB serves anything — DNS still has to propagate and the target has to pass its first health check. Give it another 1–2 minutes.

Use curl -sS, not -s. The lowercase s suppresses error messages too, so all you see is 000.

Teardown

terraform destroy fails on the subnets or VPC with DependencyViolation

The EKS security groups still exist. They were created by eksctl inside your VPC, and AWS refuses to delete a subnet that something is still attached to.

Two possibilities:

  1. Phase 13 step 4 has not finished. Wait, then re-run terraform destroy — it resumes where it stopped.
  2. eksctl delete cluster aborted before its cleanup phase. See the next entry.
eksctl delete cluster returns 404 "No cluster found" — but resources are left behind

This looks like success. The cluster is gone. But eksctl's cleanup phase never ran, because it describes the cluster first and a 404 aborts the whole command before it deletes CloudFormation stacks, IAM roles and security groups.

That is why the phase 13 checkpoint lists four commands, not one. Look for leftover CloudFormation stacks named eksctl-* and delete them from the console.

Rule for next time: always delete a healthy cluster with eksctl. If the cluster is already gone, expect manual cleanup.

Leftover security groups refuse to delete

They reference each other in a circle. AWS will not delete a security group while another one still names it in a rule, and if A references B and B references A, neither can go first. 

# break the circle first
aws ec2 revoke-security-group-ingress --group-id <SG-A> \
  --ip-permissions '[{"IpProtocol":"-1","UserIdGroupPairs":[{"GroupId":"<SG-B>","UserId":"<ACCOUNT_ID>"}]}]'

# now delete
aws ec2 delete-security-group --group-id <SG-A>
aws ec2 delete-security-group --group-id <SG-B>
CloudFormation refuses to delete a stack

A stack in CREATE_IN_PROGRESS cannot be deleted. CloudFormation will not start an operation while one is running, and EKS will not delete a node group that is still CREATING.

Do not press "Delete stack" in the console while it is creating. It fails and leaves you with DELETE_FAILED — a second stuck state. Wait for the operation to settle (ACTIVE, DEGRADED or CREATE_FAILED), then delete.

Git and GitHub

git commit says "no changes added to commit" after git add .

You ran git add . from a subdirectory. In git, . means "this directory and below" — it is relative to your working directory, not the repository root. Files one level up were never staged.

Run it from the repo root, or name the path explicitly.

A .gitignore negation (!path/to/keep) has no effect

Git cannot re-include a file if a parent directory is excluded. Git never descends into an ignored directory, so patterns for files inside it are never evaluated — no matter where they appear. 

# this ignores the folder itself → the negation below is dead code
Progress/
!Progress/notes.md

# this ignores the folder's CONTENTS → the negation works
Progress/*
!Progress/notes.md
The deploy job is skipped, always, with no error

Look at its if: condition. A github.ref == 'refs/heads/master' check on a repository whose default branch is main is never true, and a skipped job produces no failure — it just quietly does nothing.

A pushed commit contains a 600 MB Terraform provider binary

GitHub rejects any file over 100 MB. Add the ignore rules before the first terraform init: 

Terraform/.terraform/
Terraform/*.tfstate
Terraform/*.tfstate.*
Terraform/*.tfvars
Terraform/tfplan
Terraform/*.plan
!Terraform/.terraform.lock.hcl      # keep the lock file — it pins provider versions

If it already happened: git rm -r --cached Terraform/.terraform, then amend the commit.

SonarCloud

Not authorized or project not found

The properties file points at a project your token cannot write to — almost always a leftover from a tutorial. The properties file overrides anything you set in the SonarCloud UI.

Fix sonar.projectKey and sonar.organization, and verify the SONAR_TOKEN secret actually exists in GitHub. A missing secret produces the identical message.

You are running CI analysis while Automatic Analysis is enabled

SonarCloud is analysing the repo itself and you are analysing it in CI. It refuses to prevent duplicate analyses corrupting the project history.

Administration → Analysis Method → turn Automatic Analysis off. Keep CI analysis: Automatic Analysis cannot produce code coverage, which is the whole reason you set up lcov.

SonarQube Scan step is green but nothing appears in SonarCloud

Usually a branch mismatch — SonarCloud only tracks the default branch by default. Check the project's Activity page and confirm the branch name matches. Also confirm sonar.qualitygate.wait is not set if you want the job to finish quickly; with it set, the scanner polls until the gate resolves.

Glossary

Every term used in this runbook, in one place

Access entry
The EKS object that maps an IAM principal to a Kubernetes identity. Without one, an IAM role has no cluster access at all — even with AdministratorAccess.
Access policy (EKS)
A named set of Kubernetes permissions you attach to an access entry, optionally scoped to particular namespaces. Not the same thing as an IAM policy.
ALB
Application Load Balancer — a layer-7 load balancer. Created by the AWS Load Balancer Controller in response to an Ingress.
ARN
Amazon Resource Name — the unique identifier of any AWS resource. An identifier, not a credential.
aud (audience)
The token claim saying who it is for. Must be sts.amazonaws.com so a token issued for another service cannot be replayed at AWS.
Availability Zone
An isolated datacentre within a region. Your subnets span two of them; an ALB requires at least two.
CloudFormation
AWS's own infrastructure-as-code service. eksctl uses it internally, which is why eksctl-managed resources live in CFN stacks rather than any file you own.
ClusterIP
The default Service type — a virtual address that exists only inside the cluster network and is unreachable from outside.
ConfigMap
A Kubernetes object holding non-secret configuration, injected into pods as environment variables.
DependencyViolation
The error AWS returns when you try to delete something that another resource still references — most often a subnet that still has security groups or ENIs attached.
Deployment
The Kubernetes object that keeps N copies of a pod running and replaces them safely during an update.
EBS
Elastic Block Store — the disk behind an EC2 instance. Survives a stop, and is billed even while stopped.
ECR
Elastic Container Registry — the private image warehouse inside your AWS account.
EKS
Elastic Kubernetes Service — Kubernetes with the control plane operated by AWS.
eksctl
The official CLI for EKS. Creates a working cluster in one command, tracking everything in CloudFormation.
ENI
Elastic Network Interface — a virtual network card. The EKS control plane gets one per subnet; nodes get one each.
Environment (GitHub)
A named deployment target with its own secrets and optional approval rules. Declaring one changes the OIDC sub claim.
IAM
Identity and Access Management — AWS's permission system. Answers "what can you do in AWS?", never "who are you in Kubernetes?".
IAM role
An identity that can be assumed temporarily. Has two distinct policies: a trust policy (who may assume it) and permission policies (what it may do).
Ingress
The Kubernetes object that asks for a load balancer and defines routing rules. Deleting it is what deletes the ALB.
IRSA
IAM Roles for Service Accounts — the mechanism that lets a pod hold an AWS identity via a projected token, with no stored credentials.
kubeconfig
The file (~/.kube/config) telling kubectl which cluster to talk to and how to authenticate. Written by aws eks update-kubeconfig.
liveness probe
Periodic check answering "is this container alive?". Failure causes a restart.
Lockfile
package-lock.json — the exact version of every dependency. npm ci installs from it and fails if it disagrees with package.json. This is what makes builds reproducible.
NAT gateway
Lets private subnets reach the internet outbound, with no inbound path. Bills hourly regardless of traffic.
Node
An EC2 instance registered as a Kubernetes worker. Cluster-scoped, so it has no namespace.
Node group
A managed set of nodes sharing an instance type and scaling configuration.
OIDC
OpenID Connect — the standard that lets one system prove its identity to another using a short-lived signed token instead of a shared password.
Pod
The smallest unit Kubernetes runs — one or more containers sharing an address and lifecycle.
readiness probe
Periodic check answering "can this pod serve traffic now?". Failure removes it from the Service but leaves it running. This is what makes zero-downtime rollouts possible.
Region
A geographic cluster of datacentres. Everything here is in ap-south-1 (Mumbai). Resources in different regions cannot see each other.
Rollout
Kubernetes replacing pods one batch at a time when a Deployment changes. kubectl rollout status waits for it; rollout undo reverses it.
Service
A stable in-cluster address that load-balances across pods matching a label selector.
ServiceAccount
A Kubernetes identity for a pod. With the right annotation, it can be mapped to an IAM role — that is IRSA.
SPA fallback
Serving index.html for any unmatched path so client-side routes survive a page refresh. Also why an unimplemented /api returns HTML with HTTP 200.
STS
Security Token Service — issues the temporary credentials. AssumeRoleWithWebIdentity is the call OIDC uses.
sub (subject)
The token claim identifying which repo, and which branch or environment, the token came from. The most security-critical line in a trust policy.
Subnet
A range of IPs inside a VPC, tied to one Availability Zone. "Public" means its route table has a route to an Internet Gateway.
terraform.tfstate
Terraform's record of which real resources correspond to which blocks of code. Delete it and Terraform no longer knows it owns anything — it would build duplicates.
Trust policy
The rule on an IAM role stating who may assume it and under what conditions. Distinct from the permission policy.
VPC CNI
The plugin that gives each pod a real IP address from the subnet's CIDR range. Runs as the aws-node DaemonSet and needs AmazonEKS_CNI_Policy.
VPC

The four ideas that explain everything else

IdeaWhy it matters
Two tools, two states Terraform's memory is a file on your laptop; eksctl's is CloudFormation in AWS. Neither can clean up the other's work, which is why teardown has a fixed order.
IAM ≠ Kubernetes RBAC AWS permissions and cluster permissions are separate systems. An access entry is the bridge, and without one even an administrator has no cluster access.
Tags are the interface The load balancer controller discovers subnets by tag alone. No tag, no load balancer, and no error message. Nearly every silent failure traces back to this.
Your terminal is a window, not a switch AWS is a server-side state machine. Ctrl+C, a client timeout, and a console button do not stop it. When something looks stuck, run a describe — never a cancel.
